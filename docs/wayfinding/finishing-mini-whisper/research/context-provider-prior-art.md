# Context-provider routing prior art

**Scope.** This investigates the routing problem behind ticket 50 as of 2026-08-21. It uses Apple documentation and SDK headers, protocol specifications, and first-party documentation or source from the named products. “Verified” means a source states the mechanism. “Inference” is a conclusion drawn from those facts. An absent API is reported only as a bounded search result, not as a claim that nobody has ever built one.

## Short answer

MiniWhisper can identify the application receiving keys and can ask that app for its focused Accessibility window. It cannot turn that information into the PID, PTY, or active pane of a program running inside a terminal. Apple’s process APIs can enumerate a process tree, but publish no join between a terminal window or AX element and the terminal’s child process or active pane. [NSWorkspace `frontmostApplication`](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication), [Apple XNU `libproc.h`](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h), Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Versions/A/Frameworks/HIServices.framework/Versions/A/Headers/AXUIElement.h`

The closest successful prior art is **terminal-owned session identity**, not a system facility. iTerm2 has a unique session ID, knows its current session, knows the foreground job PID, and lets a program set session user variables. A terminal-specific adapter can therefore join `focused terminal session → provider ID → provider endpoint`. [iTerm2 variables](https://iterm2.com/3.3/documentation-variables.html) This is automated and correct, but it is terminal-specific. Ghostty’s documented shell integration consumes shell-originated state for prompt navigation, directory inheritance, titles, and cursor behavior; no documented external macOS API found in the examined Ghostty docs/source exposes its focused pane or that state to another app. [Ghostty shell integration](https://ghostty.org/docs/features/shell-integration), [Ghostty shell-integration source](https://github.com/ghostty-org/ghostty/blob/main/src/shell-integration/README.md)

So the first provider contract should not pretend that bundle ID solves routing. It needs one of these explicit associations:

1. **A terminal-specific broker, preferred for automatic terminal routing.** The broker runs where the terminal can name the focused session or pane. A pi extension registers an opaque provider ID and context endpoint for its terminal session. At dictation end MiniWhisper asks the broker for the currently focused provider, then calls it under a short deadline. iTerm2 demonstrates all needed pieces. Ghostty needs a new supported adapter/API, not more AX probing.
2. **A host-app integration, for GUI editors.** A plugin registers against a host-provided window/document identity that MiniWhisper can compare with its `frontmostApplication` PID and focused-window metadata. This is viable only when that host exposes the same window identity to the plugin and to MiniWhisper. It does not solve a terminal pane.
3. **An explicit active-provider lease, a practical fallback.** A provider becomes the one active provider when the user invokes its command, then pushes a bounded snapshot or accepts a pull until the lease expires. It works in Ghostty because it does not infer a pane. It is deliberately manual and must visibly show which provider won.

A Unix-domain socket with code-signing verification is the best small transport for a pi extension. XPC can provide the same verification and stronger lifecycle support, but adds a native client/service shape that is disproportionate for the first shell/Node provider. Local HTTP is easy but needs a capability token and still cannot authenticate the executable. None of these transports fixes association. They merely make the selected route reachable.

## What macOS can associate

| Fact | Verified mechanics | Routing consequence |
| --- | --- | --- |
| Frontmost application | `NSWorkspace.frontmostApplication` returns the app receiving key events. Its `NSRunningApplication` has a bundle ID and `processIdentifier`. [Apple documentation](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication) | This is an application-level key only. Every Ghostty pane shares it. |
| Focused AX window/element | The AX application element has `AXWindows`, `AXFocusedWindow`, and `AXFocusedUIElement`; an AX element has an associated PID. `AXTitle` is the visible human-readable string and the header makes it required only when the element draws a string. `AXDocument` is an available attribute, not a universal identity. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Versions/A/Frameworks/HIServices.framework/Versions/A/Headers/AXAttributeConstants.h` and `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Versions/A/Frameworks/HIServices.framework/Versions/A/Headers/AXUIElement.h` | AX can refine the target to a window and expose app-supplied title/document strings. It cannot promise either string, nor a terminal pane/process ID. MiniWhisper already obtains this access through Accessibility in [`FocusedFieldReader.swift`](../../../../MiniWhisper/FocusedFieldReader.swift). |
| Window Server owner | `kCGWindowOwnerPID` is the PID of a window’s owning process. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/CoreGraphics.framework/Versions/A/Headers/CGWindow.h` | This confirms the terminal application PID. It is not the PID of the job represented by a pane. |
| Process descendants | Apple’s `proc_listchildpids(ppid, …)` lists direct child PIDs, but the same Apple header labels the `libproc` interfaces private and subject to change. [Apple XNU `libproc.h`](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h) | **Inference:** recursively walking descendants produces a race-prone process graph, not a focus map. No examined Apple API supplies `AX window/pane → PTY → child PID`, so it cannot select among multiple pi processes in one Ghostty window. |

Accessibility is sufficient for the first two rows because MiniWhisper already checks `AXIsProcessTrusted()` before reading another app’s AX tree. It does not confer process-inspection or terminal-control privileges. [`FocusedFieldReader.swift`](../../../../MiniWhisper/FocusedFieldReader.swift)

## Terminal-hosted process advertisement

### What OSC actually carries, verified

A process writes OSC sequences into its terminal output stream. The terminal emulator interprets them. The documented sequences concern terminal state:

- **OSC 7** is a `file://host/path` current-directory report. iTerm2 treats it as the synonym for its `CurrentDir` report. [iTerm2 proprietary escape codes, “CurrentDir”](https://iterm2.com/documentation-escape-codes.html)
- **OSC 133** marks prompt start, command start, command execution, and command completion. iTerm2 documents it as the FinalTerm shell-integration protocol, semantic markup of the prompt-command-output cycle. [iTerm2 proprietary escape codes, “Shell Integration/FinalTerm”](https://iterm2.com/documentation-escape-codes.html)
- **iTerm2 OSC 1337** adds terminal-owned metadata. Its session context includes a unique `id`, `termid`, foreground `jobPid`, and the root process `pid`; its tab context exposes `currentSession`. It also supports user-defined variables set by a custom control sequence or its Python API. [iTerm2 variables](https://iterm2.com/3.3/documentation-variables.html)
- **Ghostty** injects or sources shell integration so it can recognize prompts and preserve its own terminal behavior. Its documented feature list includes prompt navigation and using the previously focused terminal’s working directory when a new terminal starts. [Ghostty shell integration](https://ghostty.org/docs/features/shell-integration)

### What OSC does not supply, verified and inferred

**Verified:** these specifications describe state transmitted *to the terminal*. OSC 7 supplies a directory; OSC 133 supplies command boundaries; iTerm2’s extra variables remain iTerm2 session state. They do not specify an API through which an unrelated macOS process asks the frontmost terminal, “which pane emitted this sequence?” [iTerm2 proprietary escape codes](https://iterm2.com/documentation-escape-codes.html), [iTerm2 variables](https://iterm2.com/3.3/documentation-variables.html)

**Inference:** OSC is an excellent provider-to-terminal advertisement channel only when the terminal exposes the matching active session to MiniWhisper or a broker. It is not a cross-terminal routing standard. Encoding a provider ID in an OSC title or a shell’s working directory would be a fragile misuse of user-visible state and would still not distinguish an active split unless the terminal exports that distinction.

### The positive iTerm2 shape

iTerm2 is the usable precedent, not a generic solution: a provider can learn the session identity available in its environment, publish its opaque ID as an iTerm2 user variable, and an iTerm2-side script can resolve the focused window/tab’s `currentSession` and its user variable. The terminal, which alone owns pane focus, performs the missing join. Its session context also proves that a terminal can know the current foreground job PID, but MiniWhisper cannot obtain that value through macOS window APIs. [iTerm2 variables](https://iterm2.com/3.3/documentation-variables.html)

For Ghostty, the examined first-party feature page and shell-integration source document shell injection, prompt behavior, SSH wrappers, and terminal environment setup, but no public focused-pane query, event stream, or arbitrary external state readback. That is a **bounded negative finding**: no drop-in Ghostty equivalent to iTerm2’s session scripting was found. A Ghostty provider needs an upstream API/adapter, or the lease fallback.

The documented URL/AppleScript examples do not identify a caller. |

**Bounded negative finding.** I found no first-party public provider-registration/context-injection protocol for Raycast, Espanso, Superwhisper, Wispr Flow, Aqua Voice, Monologue, MacWhisper, TextExpander, or LaunchBar in the materials searched. Closed-source dictation product pages can establish features, not their routing mechanism. Do not treat that absence as proof that a private integration does not exist. It does mean this research found no protocol MiniWhisper can adopt.

## Local transport comparison

| Transport | Arbitrary same-user processes? | Peer identity | Delivery suitability | Verdict |
| --- | --- | --- | --- | --- |
| Unix-domain socket | Yes, if the server publishes a filesystem socket path. | Darwin’s public SDK declares `LOCAL_PEERPID`, `LOCAL_PEERCRED`, and `LOCAL_PEERTOKEN`. `kSecGuestAttributeAudit` plus `SecCodeCheckValidity` supports checking a code object against a requirement. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/sys/un.h`, [Apple Code Signing Services](https://developer.apple.com/documentation/security/code-signing-services?language=objc) | A persistent socket gives one request/reply without process launch. It needs a tight per-call deadline. | **Best first transport.** Use a socket under an owner-only runtime directory, retrieve the peer audit token if supported at runtime, and validate an allowlisted signing requirement. Treat an unsigned pi script as an explicit user-authorized capability, not an authenticated publisher. |
| XPC | Yes, with an XPC service or a listener whose endpoint/name is made available to the peer. Apple’s header explicitly supports a Mach service advertised by a `~/Library/LaunchAgents` plist and anonymous listener endpoints transmitted over an existing connection. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/Foundation.framework/Versions/C/Headers/NSXPCConnection.h` | Since macOS 13, a listener can set a code-signing requirement and XPC rejects new peers that do not match it before the delegate. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/Foundation.framework/Versions/C/Headers/NSXPCConnection.h` | Asynchronous request/reply and interruption/invalidation handlers are built in. It needs a native client/helper and bootstrap design. | **Strong alternative** for a signed provider ecosystem. No App Group appears in this non-sandboxed, per-user listener path, but a named service still needs a launchd or endpoint-distribution plan. |
| Local HTTP on loopback | Yes. | **Inference:** TCP peer address proves only loopback, not which same-user executable connected. Use a random bearer capability, but that authenticates possession rather than code identity. | Request/reply is easy from Node/shell, but a server start or connection timeout belongs outside the cleanup critical path. | Reasonable prototype transport, weaker trust. Bind only to loopback and never trust payload merely because it arrived there. |
| Distributed notifications | Yes, as a broadcast between tasks. [Apple `DistributedNotificationCenter`](https://developer.apple.com/documentation/foundation/distributednotificationcenter) | Apple says it is not secure and payload is untrusted. [Apple documentation](https://developer.apple.com/documentation/foundation/distributednotificationcenter) | Apple says delivery latency is unbounded and notifications may drop when the server queue fills. | **Dead end** for pull or delivery-critical context. At most use it as a lossy wake-up hint for cached state. |
| URL scheme | Any process may ask the system to open the registered app with context data. [Apple custom URL schemes](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app) | **Inference:** the handler receives a URL, not an authenticated peer connection. | May activate/launch the receiver; it is one-way unless another channel replies. | **Dead end** for dictation-end pull. Fine only for setup or a user-visible explicit command. |
| Pasteboard | Any process with pasteboard access can write/read a named board. `changeCount` only records ownership changes. [Apple `NSPasteboard.changeCount`](https://developer.apple.com/documentation/appkit/nspasteboard/changecount?language=objc) | No writer code identity is exposed by this API. | Polling or ownership-change checks are state observation, not request/reply. It risks overwriting or exposing user clipboard data. | **Dead end.** |
| Watched file / FSEvents | Any process able to write the file can publish a snapshot; FSEvents watches paths. [Apple File System Events](https://developer.apple.com/documentation/coreservices/file_system_events) | Filesystem owner/mode can constrain UIDs, not identify a signing identity. | The FSEvents API takes a latency parameter, so it is intentionally an event stream rather than a bounded RPC. [Apple File System Events](https://developer.apple.com/documentation/coreservices/file_system_events) | **Dead end** for pull. A useful crash-resilient cache behind a socket/XPC notification, if needed. |

The identity entries marked inference are ordinary consequences of the documented APIs, not claims of a security guarantee. The verified security mechanism is the audit-token/code-requirement path on Unix sockets or XPC. A code identity also answers “which publisher connected,” not “which terminal pane is focused.”

## Existing protocols assessed

- **MCP: do not adopt as the routing protocol.** MCP standardizes JSON-RPC over a client-launched stdio subprocess or a Streamable HTTP endpoint, with optional sessions. It does not define a macOS foreground-app, window, terminal, or pane identity. It could frame a provider’s request once MiniWhisper has selected it, but then adds a tool-server lifecycle where one bounded `context` RPC would do. [MCP transports](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports)
- **LSP: do not adopt.** LSP describes client/server initialization and permits stdio, socket files, or sockets. Its client launches or otherwise configures a server for an editor/workspace, so the editor already owns the association that MiniWhisper lacks. [LSP 3.18 specification](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.18/specification.md)
- **Accessibility: not a two-way provider bus.** AX exposes app-supplied UI elements and attributes, plus their owning application PID. The documented attributes do not carry arbitrary external-provider registration or descendant-process identity. A cooperative host app could publish a window/document identifier in its own accessibility representation, but that is host-specific integration, not a channel a pi process can attach to. Apple SDK `/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ApplicationServices.framework/Versions/A/Frameworks/HIServices.framework/Versions/A/Headers/AXAttributeConstants.h`

## Decision constraints for ticket 50

1. Define routing as a separate required capability: `provider ID` plus a **focus authority** that can map the currently focused target to that ID. Registration, transport, and a provider’s claimed host PID are not focus authority.
2. Start with Unix socket request/reply and a bounded cached snapshot. Verify a signed peer where available; make trust of unsigned pi extensions a clear user decision. The cleanup path must time out and proceed without provider context.
3. Ship the explicit active-provider lease before claiming Ghostty support. It gives the pi use case a correct, visible manual path now. Automatic support waits for a terminal-specific adapter. iTerm2 is a feasible proving ground because it owns and exposes session identity. Ghostty does not yet have a verified equivalent.
4. Do not use descendants, bundle IDs, window titles, OSC 7, OSC 133, distributed notifications, clipboard, or a watched file as the authoritative terminal-pane key. They are either too coarse, terminal-internal, lossy, or unauthenticated. The operating system has not hidden a secret pane router in Accessibility. It would have been convenient.

## Addendum, 2026-08-21: Ghostty's negative is wrong

The bounded negative above searched Ghostty's documentation and shell-integration source. It did not open the scripting definition, and that is where the answer was. Ghostty ships an sdef and the focused pane is queryable over Apple events **today, on stable**, by any process the user has granted Automation.

Parsed from the installed `/Applications/Ghostty.app/Contents/Resources/Ghostty.sdef` (Ghostty 1.3.1):

| class | properties | elements |
| --- | --- | --- |
| `application` (`capp`) | `name`, `frontmost`, `front window`, `version` | `window`, `terminal` |
| `window` (`Gwnd`) | `id`, `name`, `selected tab` | `tab`, `terminal` |
| `tab` (`Gtab`) | `id`, `name`, `index`, `selected`, `focused terminal` | `terminal` |
| `terminal` (`Gtrm`) | `id`, `name`, `working directory` | — |

`application → front window → selected tab → focused terminal → id` is a complete path from "which app has focus" to "which pane has focus", and the terminal `id` is stable. Verified live rather than read:

```sh
osascript -e 'tell application "Ghostty" to get id of focused terminal of selected tab of front window'
# A09FBC5C-531E-4D9E-AEA8-9E1CA497ECEF
```

What the sdef does **not** carry on 1.3.1 is the pane's tty, so the join from a pane id to the process living in it is still missing from Ghostty itself. Ghostty tip (0.4.0) adds `tty` to the terminal class, which closes it outright — recorded in [ghosttykit's spawn-token design](../../../../../ghosttykit/docs/designs/04-spawn-token-terminal-binding.md), which verified the same sdef against the same installed version and is explicitly structured to be deleted when tip lands.

And the broker from route shape 1 is already built and daily-driven. `ghosttykitd` speaks Apple events to Ghostty and maintains tty↔terminal-id bindings, claimed at spawn with single-use tokens precisely because the focused-terminal guess raced; `gty terminal-id` resolves a caller's own tty to its terminal id. A provider inside a pane can therefore name itself in terms the broker already understands, and MiniWhisper can ask for the focused terminal id over the same Apple-event path without going through the daemon at all.

So constraint 3 above inverts. Ghostty is not the terminal that has to wait for the lease — it is the one with a working focus authority, an existing broker, and a project-mate willing to add the registry. iTerm2 remains a second implementation rather than the proving ground. The lease keeps its place as the fallback for every terminal that is neither.
