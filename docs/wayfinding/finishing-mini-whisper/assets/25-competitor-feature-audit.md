# Competitor feature audit: Wispr Flow, Aqua Voice, Monologue

Research snapshot: 2026-08-04. Asset for [Competitor feature audit: Wispr Flow, Aqua Voice, Monologue](../tickets/25-competitor-feature-audit.md). This records current public evidence and proposed stakes; it does not choose product behavior.

## Scope and confidence

This supersedes [Dictation app feature survey](01-dictation-app-feature-survey.md), which was a useful broad feature matrix but treated all three products largely as marketing references. This pass used current vendor documentation, changelogs, and guides first; claims marked **vendor claim** are not independently reproduced. One third-party review was found for Wispr's Google Docs/Command Mode experience, but it did not establish the underlying context or insertion mechanism, so it is not relied on for product facts. No source found documents a target-specific contract for Google Docs' canvas editor or nvim.

The important change is not that these apps acquired a few more switches. They increasingly treat dictation as a contextual editing pipeline: capture target/selection context, choose formatting, preserve a recovery path, and teach the capability while it is relevant. MiniWhisper already has a deliberately smaller version of the first and recovery paths; the boundary matters.

## Workflows the first survey under-weighted

### One-utterance correction versus editing an existing selection

Wispr's Backtrack and Monologue's false-start cleanup act while the utterance is still one unit of work. Aqua's Edit Mode is a separate interaction: the user has selected existing text, the same hold key switches interpretation, and a visible selection-count chip tells them why. Its most useful details are not the rewrite model: selection makes the scope explicit; the fallback for huge selections and browser chrome prevents surprises; edit history records what was selected, said, and produced; and voice undo is confined to that edit chain ([Aqua Edit Mode](https://aquavoice.com/guide/edit-mode)).

This separates two problems that the first survey conflated:

1. Repairing a self-correction before delivery is transcript cleanup. It can be evaluated with the later gateway cleanup pass, alongside the risk of changing the user's intended wording.
2. Rewriting already-present text is a selection-capture, replacement, undo, and privacy feature. It is not “cleanup after transcription,” even if it calls the same gateway.

Wispr's Command Mode is more expansive than Aqua's: it requires a separately enabled paid experimental shortcut, may transform a selection or answer without one, and has access to past dictations/notes ([Command Mode](https://docs.wisprflow.ai/articles/4816967992-how-to-use-command-mode)). That breadth is a useful contrast, not a MiniWhisper target.

### Vocabulary correction, deterministic replacement, and snippets are separate

Wispr now explicitly separates word boosting, one-to-one misspelling replacement, snippets, and optional automatic dictionary addition from corrections ([dictionary guide](https://docs.wisprflow.ai/articles/4052411709-teach-flow-your-words-with-the-dictionary)). Aqua has both a manual difficult-word dictionary and general phrase replacements ([dictionary](https://aquavoice.com/guide/dictionary), [replacements](https://aquavoice.com/guide/replacements)). Monologue presents automatic personal-vocabulary accumulation, but the public documentation inspected does not explain its correction/review rule ([product site](https://www.monologue.to/)).

The useful part for MiniWhisper is narrower: a wrong proper noun should lead directly to a reviewed vocabulary addition, without making the user hunt through settings. That matches the existing quick-add requirement in [Dictionary: vocabulary hinting](../tickets/13-dictionary.md). Automatic remapping and spoken snippets remain a different product category.

### Recovery is a target-state problem, not merely “history exists”

The products now make a distinction the first survey did not spell out:

- Wispr preserves the previous clipboard only after verified successful delivery; failed delivery intentionally leaves the new text available to paste ([paste troubleshooting](https://docs.wisprflow.ai/articles/7971211038-fix-text-not-pasting-after-dictation)).
- Monologue detects destination change/no active field and copies instead of sending text to a different app ([changelog](https://feedback.monologue.to/changelog)).
- Aqua retains enough local audio to replay and re-transcribe for three days ([History](https://aquavoice.com/guide/history)); its Edit Mode additionally preserves source/result/spoken request ([Edit Mode](https://aquavoice.com/guide/edit-mode)).

Those are different recovery contracts: immediate deliverability, correct-target safety, and diagnostic/reprocessing evidence. MiniWhisper already has ownership-aware clipboard restoration and paste-last; later history should decide whether retained audio earns the extra privacy/storage cost.

### Onboarding teaches a capability at its point of failure

The current examples share a pattern worth preserving as a design question. Wispr's onboarding makes the user practise the primary action and gives microphone failures a specific remediation path ([first dictation](https://docs.wisprflow.ai/articles/6409258247-starting-your-first-dictation)). Monologue sequences permissions, explains the reason for each, verifies them after relaunch, and exposes Reset Onboarding ([setup](https://help.monologue.to/en/articles/14178193-quick-setup-guide)). Aqua's new editing capability is introduced through a short real-pipeline tour, not a static help article ([Edit Mode announcement](https://aquavoice.com/blog/introducing-edit-mode)).

For a menu-bar app, this is more useful than a feature catalogue: a permission that changes, a missing microphone, or a new behavior needs a re-enterable proof path. The existing keyboard-navigation stake still owns making the current onboarding reachable without a mouse; it does not answer capability recovery or later feature tours.

## Proposed stakes for a grilling session

1. **Selection voice editing** — should a user-selected existing range be captured, sent through the sanctioned cleanup gateway, replaced, and locally undoable? Establish selection acquisition, target limits, privacy disclosure, failure fallback, and whether the current hold key may infer this mode.
2. **Onboarding capability recovery** — how should a one-person menu-bar app re-check permissions/device/model readiness, reset first-use practice, and introduce later high-risk features without reintroducing a permanent dashboard?

## Evidence gaps

- No public source established how any of the three reads or writes semantic context in Google Docs' canvas editor. The support claims establish attempted delivery, not a correct caret/text contract.
- No public nvim-specific source was found for any product. Aqua documents terminal/CLI use; Flow documents terminal exceptions; neither proves nvim behavior.
- Product pages and vendor blogs make accuracy/latency claims, but this audit did not independently run a corpus or inspect private client implementations. Their model-quality numbers are deliberately not used to choose MiniWhisper's local engine.
- Monologue's public materials currently advertise offline transcription while a changelog describes a dictate API. The per-dictation routing, retention, and exact local-model capability were not established from the inspected sources.
- Aqua's Deep Context is described as screen reading, and Wispr's FAQ names AX/OCR components, but neither publishes a per-app data shape, bounds, or target fallback. Do not treat either as a safe implementation blueprint.
