So: an unreadable history.json — corrupt, or written by a newer build and rejected by the version gate — survives launch untouched, and is then silently
overwritten by the first dictation with a log containing exactly one entry. The user's history is gone with an .error line in the unified log as the only
trace.
That defeats the thing HistoryLog.init(from:) was built to do. Its comment says decoding "rejects files from a version it does not know rather than
misreading them" — but rejecting the read while permitting the write is worse than misreading, because misreading is recoverable and truncation is not. The
postmortem this whole ticket came from was about 109 unrecoverable WAVs. This is the same failure with the transcripts.
The detection already exists two lines away. Consult it before the write: if loadError != nil, drop the entry (with its audio) rather than clobber the file,
or move the unreadable file aside first and start clean deliberately. Either is defensible; silently overwriting is not.
