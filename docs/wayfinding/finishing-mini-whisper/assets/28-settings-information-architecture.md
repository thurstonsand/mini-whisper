# Settings information architecture: how comparable apps organize configuration

Research snapshot: 2026-08-04. Asset for [Settings information architecture: how other apps organize configuration](../tickets/28-settings-information-architecture.md). This collects evidence and recommends a shape for the coming design conversation; it does not select product behavior.

## Scope and reading of the evidence

This is an information-architecture survey, not a repeat of [Competitor feature audit](25-competitor-feature-audit.md). “Vendor claim” means a vendor documentation or release-note assertion, not independently reproduced behavior. Public documentation often describes a setting without exposing the surrounding UI; where it does, this report names only the established pane or tab and leaves the rest unknown.

MiniWhisper today has one persistent JSON value for a physical hotkey and sounds, at `~/Library/Application Support/<channel>/settings.json`; the menu owns sounds, launch at login, copy-last, and repair. The input device is observed but not selected, and model readiness/download is currently onboarding-owned ([`Channel.swift`](../../../MiniWhisper/Channel.swift), [`SettingsStore.swift`](../../../Packages/HotkeyListener/Sources/HotkeyListener/SettingsStore.swift), [`AppFeature.swift`](../../../MiniWhisper/AppFeature.swift)). `writeDebugWAV` still writes every capture to the temporary directory; History has already settled that its owned store replaces it ([`AudioCaptureClient.swift`](../../../MiniWhisper/AudioCaptureClient.swift), [History — Decisions carried](../tickets/11-history.md)).

## The useful placement patterns

There are three viable shapes in the evidence:

1. **A real app shell with History as a first-class destination** — Wispr, MacWhisper, and Hex. It gives recovery search, playback, deletion, and provenance room to grow. It also makes the first window larger in ambition than a preferences sheet.
2. **History inside settings** — Aqua. One window and a short navigation model, but it conflates an active recovery task with a configuration task. It is more defensible if history is short, private, and rarely revisited.
3. **Recent items in the status menu** — Monologue. The fastest recovery path and lowest surface-area cost, but a status menu does not scale to audio replay, retention explanation, diagnostics, search, or a long corpus. It is a complement to a window, not enough for settled MiniWhisper History.

Every product with enough surface area duplicates one or two immediate actions outside the main configuration window: Wispr exposes mic/history/paste-last in its status/Flow menu, Superwhisper exposes the microphone there, and Monologue exposes recent transcripts there ([Wispr navigation](https://docs.wisprflow.ai/articles/5096240724-navigating-the-wispr-flow-app-desktop-ios-and-android), [Superwhisper Sound](https://superwhisper.com/docs/get-started/settings-sound), [Monologue recent transcripts](https://help.monologue.to/en/articles/14178198-access-recent-transcripts)). The pattern is “window for management; menu for recovery,” not “put every control in the menu.”

## Hex: the implementation shape worth borrowing

Hex is unusually useful because the UI and persistence are inspectable. At commit `881c46f`, it does **not** use a SwiftUI `Settings` scene. `HexApp` owns a `MenuBarExtra`; its Settings… item calls an app-delegate method which retains and foregrounds one AppKit `NSWindow` hosting the root `AppView`. The app deliberately suppresses startup foreground windows for login launches; a normal launch presents/activates the window ([`HexApp.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/App/HexApp.swift#L11-L54), [`HexAppDelegate.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/App/HexAppDelegate.swift#L27-L126)).

That root reducer owns child Settings, History, and transcription features plus `activeTab`; the view scopes them into the sidebar. `SettingsFeature` has a file-shared `HexSettings`, nested model-download state, transient hotkey-capture state, device list, and permission state. It is a plausible TCA shape for MiniWhisper: one root window feature scopes content destinations, and settings controls mutate the same authoritative file model rather than becoming a second preference store ([`AppFeature.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/Features/App/AppFeature.swift#L14-L90), [`SettingsFeature.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/Features/Settings/SettingsFeature.swift#L38-L118)).

Its persistence is `@Shared(.fileStorage(.hexSettingsURL), default: .init())`, an explicit `Codable` `HexSettings` at `~/Library/Application Support/com.kitlangton.Hex/hex_settings.json`; history metadata is a separate shared JSON file and recordings are separate WAVs. The settings schema does default-aware decoding/migration. This supports, rather than replaces, MiniWhisper’s fixed “human-editable JSON stays authoritative” requirement ([`AppHexSettings.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/Models/AppHexSettings.swift#L8-L29), [`HexSettings.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/HexCore/Sources/HexCore/Settings/HexSettings.swift#L10-L299), [`HistoryFeature.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/Features/History/HistoryFeature.swift#L35-L56)).

Its hotkey recorder is also the relevant interaction precedent: while capture is active it subscribes to the global event stream, accepts modifier-only or key-plus-modifier chords for the recording shortcut, permits Escape to cancel, then persists normalized modifiers. The runtime transcription feature ignores events during capture and runs the persisted chord through `HotKeyProcessor`; separate paste-last capture rejects a bare key. That establishes a recording field as an explicit temporary mode, not a text field pretending to be a shortcut editor ([`SettingsFeature.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/Hex/Features/Settings/SettingsFeature.swift#L134-L211), [`HotKeyProcessor.swift`](https://github.com/kitlangton/Hex/blob/881c46f236f5/HexCore/Sources/HexCore/Logic/HotKeyProcessor.swift#L10-L537)).

## macOS convention and mechanism

Apple’s HIG says a macOS custom settings window typically has a toolbar for panes, that the active pane remains evident, and that settings should be reachable from the app menu; task-specific options belong in the task instead ([HIG: Settings](https://developer.apple.com/design/human-interface-guidelines/settings)). A sidebar is a reasonable SwiftUI expression of that stable pane navigation; the HIG does not require the literal legacy icon toolbar.

A SwiftUI `Settings` scene is a scene specifically for app settings. Declaring it enables the app’s Settings menu item and lets SwiftUI manage showing/removing its settings window for that command and its shortcut. It does **not** create bindings, tabs, validation, a TCA store, JSON persistence, or any information architecture; those remain MiniWhisper code ([Apple: `Settings`](https://developer.apple.com/documentation/swiftui/settings)). On macOS 14+, a `SettingsLink` opens or foregrounds that scene, and `@Environment(\.openSettings)` lets a view set a selected pane then open it ([Apple: `SettingsLink`](https://developer.apple.com/documentation/swiftui/settingslink), [Apple: `openSettings`](https://developer.apple.com/documentation/swiftui/environmentvalues/opensettings)).

For an LSUIElement/status-only app, the missing Dock icon is not a reason it cannot have a settings window: `MenuBarExtra` and `Settings` are SwiftUI scenes, and `SettingsLink`/`openSettings` provides the public presentation route from a menu-bar extra. The HIG source inspected does not contain menu-bar-agent-specific settings guidance. The architectural choice is thus practical: use `Settings` when the only window is truly configuration; use a named `Window`/AppKit-owned window when the same surface is also History and other app content. Hex chose the second because History is a root destination, then explicitly foregrounds that one window.

## Placement exercise for the settled History inputs

| Shape | Home for recorder, sound, login, device, model | Home for transcript/audio retention and audio-storage switch | Home for History |
| --- | --- | --- | --- |
| Preferences tabs | **Dictation** (recorder, input device, sounds); **General** (launch at login); **Model** (status/download) | **Storage** or **History** tab. Put both TTL pickers and the audio switch together, because the switch changes whether audio has a retention meaning. | **History** tab, Aqua-style. Compact, but recovery competes with settings density. |
| One sidebar application window | **Dictation** (recorder, device, sounds); **General** (login); **Model** (status/download) | **History** destination, with a small “Storage” section at its top/empty state. The same TTL preset control appears twice only if one is a summary/link, never independently mutable. | Dedicated **History** sidebar destination, Hex-style. This matches recovery as primary. |
| History window plus settings sheet | Settings sheet contains Dictation, General, Model, Storage; history window contains records | Storage in the settings sheet, linked from History | Separate history window. Clean separation, but two window identities and navigation routes for a one-person utility. |

The settled values have a natural wording wherever they land: **Keep transcripts** and **Keep recordings** use the same 1 day / 7 days / 30 days / 90 days / 1 year / Forever preset menu; transcript defaults to Forever; recordings start enabled with a 3–7 day default. Audio storage must lead with its recovery consequence, not generic diagnostics: “Keep recording audio for replay and re-transcription.” The disabled state should make its retention picker unavailable rather than silently retaining an irrelevant preference ([History — Decisions carried](../tickets/11-history.md)).

## Options MiniWhisper has not yet staked

These are options to take to a later grilling, not recommendations to adopt.

- **Ranked/automatic microphone fallback.** Wispr asks users to rank inputs and automatically switches to the highest available mic when a headset connects or the laptop closes, rather than treating input choice as one fixed device ID ([Wispr Flow what’s new](https://wisprflow.ai/whats-new)). MacWhisper’s System Default / Fixed / Priority List makes the same policy explicit ([MacWhisper release notes](https://macwhisper-site.vercel.app/release_notes.html)). This is distinct from merely adding a device picker, and directly addresses a disconnected or clamshell microphone.
- **A re-enterable microphone proof.** Monologue’s setup includes live meter feedback and a device dropdown, then retains level monitoring in Mic & audio ([Monologue microphone settings](https://help.monologue.to/en/articles/14178194-microphone-settings)). MiniWhisper has a pill device label and onboarding, but no named later “is this microphone receiving speech?” check. This could belong with capability recovery, not ordinary settings.
- **Data policy as a first-class control.** Wispr’s vendor-described normal / delete-after-24-hours / never-store choices and cloud-sync separation show a plain-language storage policy rather than a hidden file-management detail ([Wispr Flow what’s new](https://wisprflow.ai/whats-new)). MiniWhisper’s local-only equivalent is narrower: explicit retention and audio evidence, but it needs clear total deletion behavior when audio storage turns off.
- **Settings deep link / automation hook.** Superwhisper documents `superwhisper://settings` as an automation route ([Superwhisper Settings](https://superwhisper.com/docs/get-started/settings)). It is not an MVP need, but it is an option if MiniWhisper later has a repair notification or an agent-driven support workflow that must target one pane.
- **Per-capability recovery cards, not a permanent dashboard.** Monologue can reset onboarding from the status menu and Aqua launches a real Edit Mode tour from a Settings card ([Monologue setup](https://help.monologue.to/en/articles/14178193-quick-setup-guide), [Aqua Edit Mode](https://aquavoice.com/guide/edit-mode)). This supports the separately proposed onboarding-capability-recovery stake: model/device/accessibility problems can route to a focused proof, rather than forcing users to rediscover first-run onboarding.

## Recommendation for Settings UI to discuss

Recommend one ordinary, resizable application window with a stable sidebar: **History**, **Dictation**, **Model**, and **General**. Make **History** the initial destination after a completed dictation or recovery notification; make **Dictation** the initial destination from a “Settings…” menu command until History exists. Keep the menu bar deliberately small: Paste Last Transcript, perhaps a short Recent list once History has it, status/repair actions, Open MiniWhisper, Quit. Do not preserve controls there merely because they were there before.

**Dictation** owns the record-key capture control, input device policy, and sounds. **Model** owns readiness, version/size where known, download/progress/retry, and the fixed local/offline fact. **General** owns launch at login and future non-recording application behavior. **History** owns the records and their audio replay/re-transcription/deletion, and has a compact **Storage** section for transcript retention, audio-storage toggle, and audio retention. This is Hex’s one-window/TCA root shape with the stricter recovery priority already settled by MiniWhisper History.

The tradeoff is deliberate: this is more window than a conventional preferences sheet and it commits sidebar names early. In exchange, it prevents History from being squeezed into a settings tab, gives its recovery evidence enough room, keeps JSON authoritative behind one TCA root, and avoids two window systems. A future `Settings` scene would be simpler only if History becomes a separate window; current settled requirements point the other way.

## Evidence gaps

- No public source inspected establishes Aqua’s complete desktop settings navigation, or the locations of its microphone, sounds, launch-at-login, and hotkey controls. Its overview establishes only a Settings History tab and multiple hotkeys.
- No public source inspected establishes Monologue’s full tab count, history retention/audio policy, launch-at-login setting, or local-model UI.
- Superwhisper’s docs establish configuration areas and screenshoted Sound/Advanced pages, but not a definitive current navigation hierarchy nor its History UI location.
- MacWhisper’s release notes and support index establish several destination names but not its complete current settings sidebar. The Context7 support index is a structured extraction of vendor help, not a direct product run; treat pane taxonomy beyond the cited navigation strings cautiously.
- No competitor public evidence inspected states whether its macOS settings window is SwiftUI `Settings`, SwiftUI `Window`, or AppKit. Hex is the exception because its source proves the latter.
- Apple’s HIG establishes the general pane/navigation convention, but the inspected HIG material does not give a menu-bar-only/LSUIElement-specific preference-window prescription. Apple API documentation establishes public opening mechanisms, not the product decision of `Settings` versus an app-content window.
