# Cleanup model benchmark: fast OpenAI-compatible endpoints

Research checked 2026-08-17. This is a screening survey, not a model choice: published decode speed is not MiniWhisper's blocking latency, and no provider score predicts whether its cleanup will preserve a spoken technical dictation. The runnable comparison lives at [`38-cleanup-model-benchmark/`](38-cleanup-model-benchmark/README.md).

## What the benchmark must optimize

Ticket 18 makes cleanup `transcribe → cleanup → deliver`, with a 10-second error/timeout backstop and a roughly three-second skip affordance. The important measurement is consequently final cleanup response wall-clock time at the actual gateway and network location, not an accelerator's decode-only throughput. TTFT matters more than TPS for a short cleanup response, but neither alone includes queueing, a field-context prompt, or the network.

The dev corpus is a version-1 `HistoryLog` at `~/Library/Application Support/MiniWhisper Dev/History/history.json`. It currently contains 121 entries, all with `original.text`, 110 target-app records, no retranscriptions, and **no persisted field context**. The harness reads it only and uses `original.text` rather than `currentText`, a retranscription, or `delivery.text`. This honors [`HistoryEntry`](../../../Packages/History/Sources/History/HistoryEntry.swift): original ASR is immutable evidence, retranscriptions are later opinions, and delivery text is the final joined outcome. Current history therefore supports raw-transcript quality and latency measurement now; a later cleanup/context storage design must persist context separately if it wants context-aware replay.

The first-party sources make two things clear. Cerebras, Groq, and SambaNova advertise unusually high **decode** rates for a shared 120B-class candidate, while Fireworks and Together sell flexibility/serving controls more than a comparable static latency rate card. None supplies the only result ticket 18 needs: end-to-end short-response latency through this user's path. A 100–3,000 TPS claim also becomes a fraction of a second for a 10–30-token cleanup; request startup and queue time will dominate if they are poor.

## Harness

[`cleanup_benchmark.py`](38-cleanup-model-benchmark/cleanup_benchmark.py) is standard-library Python 3. It accepts an endpoint base URL, API key or key environment variable, and one or more model IDs. For each usable entry it sends one conservative chat-completion request with the raw transcript and target-app identity, then prints:

- request-start to final-response-body wall-clock latency;
- a unified raw → cleaned diff for quality review; and
- per-model successful-run median, p95, minimum, and maximum.

It does not request tools or structured output, so the basic path avoids the known provider incompatibilities. It deliberately emits no corpus artifacts to disk. The terminal output is private and should be handled accordingly. The harness recognizes a future `fieldContext`, `focusedTextContext`, or `cleanupContext` record when present, but does not invent a new History schema. Its [README](38-cleanup-model-benchmark/README.md) has ready-to-run commands and explains the history/context contract.

A non-network smoke test passed on this machine:

```sh
python3 -m py_compile docs/wayfinding/finishing-mini-whisper/assets/38-cleanup-model-benchmark/cleanup_benchmark.py
python3 docs/wayfinding/finishing-mini-whisper/assets/38-cleanup-model-benchmark/cleanup_benchmark.py --help
```

## This machine's ballpark status

Only obvious process environment names were inspected: `OPENAI_API_KEY`, `CEREBRAS_API_KEY`, `GROQ_API_KEY`, `FIREWORKS_API_KEY`, `TOGETHER_API_KEY`, and `SAMBANOVA_API_KEY` (and their provider prefixes). None was exported, so **no external request and no official-endpoint ballpark run occurred**. No Keychain, shell dotfile, or app configuration was searched, and no application was activated.

To make each comparison runnable, create an API key in the named provider's official console, export the exact variable for the one benchmark shell, and run the corresponding README command. The required values are:

## Default-model shortlist for the decision session

The following is a test order, not a selection:

1. **Groq GPT-OSS 20B** — cheapest published fast baseline (1,000 TPS; $0.075/$0.30). It may be enough for strictly mechanical cleanup, but must prove it does not over-correct technical dictation.
2. **Cerebras GPT-OSS 120B** — highest published decode rate (about 3,000 TPS) while keeping a 120B-capability control; cost is higher than Groq/SambaNova, but output lengths are tiny.
3. **Groq GPT-OSS 120B or SambaNova GPT-OSS 120B** — same class under an independent serving stack (500 versus 700+ published TPS) to separate model quality from endpoint latency. Run one or both according to available accounts.
4. **The work-gateway Haiku 4.5 and GPT-5.6-luna routes** — product-relevant controls. They can win despite slower public figures because sanctioned routing, proximity, and actual cleanup quality are the real constraints.

Use the same fixed History sample, a small output cap, and at least a cold-ish first call plus repeated requests. Compare median and tail final wall-clock time, then eyeball every diff for forbidden invention, missed symbols, capitalization/spacing against the field context, and failures. Any contender regularly crossing the ~3-second skip point is difficult to call a comfortable default even if it stays inside the 10-second fallback ceiling. The decision belongs to ticket 18's grilling session.
