# Recommended cleanup providers: a shortlist over the custom endpoint

## Question

Make picking a good cleanup setup easy: a curated shortlist of well-known providers/models ("recommended" cleanups) layered over the existing custom-endpoint surface, which always remains. What earns a spot on the shortlist is performance-test-driven — the [benchmark harness](../assets/38-cleanup-model-benchmark.md) and real perf runs feed it. Design the pane UX (how a recommendation prefills endpoint/model, how it coexists with Custom), the update story for the list, and the criteria for inclusion. Depends on the shipped cleanup pass and on [native endpoints research](40-native-llm-endpoints.md) if provider-specific APIs join the menu.

## Scope notes (2026-08-20, user)

- The shape is **presets**: well-known sources — Groq, Cerebras, and a local option like "S1-mini" by "Superwhisper" ([ticket 45](45-local-cleanup-s1-mini.md)) — that prefill or replace the endpoint/model surface, with Custom always remaining.
- Presets open the door to **per-preset custom prompts**: a model-specific built-in prompt (or prompt fragment) where a model needs one — S1-mini's fixed control-line format is the extreme case; a fast host's quirks (lowercased first words, typographic hyphens) could be patched per-preset without touching the shipped default.
- **Cohere is a preset candidate** (user, via superwhisper's [S1 post](https://superwhisper.com/blog/s1) leaning on Cohere): Canadian, and its [Compatibility API](https://docs.cohere.com/docs/compatibility-api) speaks the OpenAI chat-completions shape our client already talks — so a Command-family preset costs nothing architecturally. Needs an API key and a benchmark run through asset 38 before it earns the list; superwhisper's own enthusiasm is for Cohere's ASR model ([ticket 15](15-second-engine.md)'s revisit), so the cleanup case rests on our measurements alone.
- First measured runs (in the [benchmark asset](../assets/38-cleanup-model-benchmark.md)): Cerebras gpt-oss-120b ~394 ms is the leading full-contract fast candidate; Cerebras gemma-4-31b deterministically hallucinates dictionary terms and is disqualified; Groq gpt-oss-20b/120b ~700 ms; frontier gateway ~3 s and alone in passing all boundary probes.
- **Dictionary three-way (corpus round 2):** with vocabulary staged in the DICTIONARY block, bare-ASR + gemini scores 18/18 recall with 0/8 traps; the recognition sidecar's best is 16/18 with 5/8, and boosting *before* the LLM only hands it fluent, unflaggable errors. When cleanup is on, the sidecar is harmful; its remaining case is +98 ms vs ~+2 s and being the whole vocabulary story when cleanup is off. Boost threshold sweep found no good operating point (0.65–0.85 bite the same traps while bleeding recall). Whether to suppress boost when cleanup is configured is an open design decision.
- **Full frontier (round 2 addendum, Parakeet rows):** gemini-3.6-flash 19/27 @ ~2.5 s (crown); claude-haiku-4-5 via Anthropic's OpenAI-compat endpoint 17/27 @ 696 ms e2e — dominates gpt-5.6-luna outright (same score, quarter latency; luna has no remaining argument); Cerebras gpt-oss-120b 15/27 @ 420 ms but with rule failures (untranslated `period` twice — once on the no-instruction-following invariant — and a forbidden trailing period on the bare-ending entry); s1-mini 12/27 @ 107 ms offline. Dictionary three-way across four models: every model bites strictly more traps on boosted input and recovers zero additional terms; haiku adds 94.4% recall at +671 ms, gpt-oss 83.3% at +381 ms, so even the sidecar's latency argument thins to the cleanup-off case. Both new endpoints accepted the app's request body unchanged (haiku alias resolves to claude-haiku-4-5-20251001; Cerebras' extra `reasoning` field needs no shaping change).
- **Round 3 (routes):** the gateway is not why gemini is slow — direct Google API saves 618 ms at the median (247 ms paired) with an identical 19/27 and failure set; the thinking tail is the model's own. Haiku on the Claude subscription (Agent SDK, OAuth verified, API key scrubbed) scores the identical 17/27 at 627 ms warm / 993 ms fresh vs 638 ms metered — subscription parity is real, but adaptive thinking must be disabled (costs 4.4 s and two entries) and persistent sessions contaminate output with accumulated transcript context. Profile stacks decided in [results/profiles-recommendation.md](../assets/43-dictation-corpus/results/profiles-recommendation.md); gpt-oss-120b needs its ticket-48 prompt pass before any profile ships it.
- **Subscription-parity asterisk (post anti-overfit tooling):** the Agent SDK route is not score-neutral after all — Claude Code injects ~140 tokens of its own user-context framing (email, date), measured at 16.25/25 vs 19.00/25 metered on the same prompt and n. Round 3's "identical 17/27" comparison was too coarse to catch it. Consequence: the subscription runs proposers and screens; anything scored for the record runs metered. A native integration (this ticket's presets) would use the API directly and is unaffected.
